# SciRSSAgent UI 设计与实现规范

本文档是 SciRSSAgent 的 UI 设计、实现与验收规范。修改 `web/` 下的界面前应先阅读本文；当产品的布局基线、交互约定或视觉语言发生变化时，应在同一改动中更新本文。

## 1. 核心原则

### 1.1 先定位问题层级

界面不协调时，先判断问题属于颜色、空间、层级、组件状态、信息架构还是产品行为，不要直接通过增加或删除边框来试错。

- 同时检查页面背景、内容 Surface、表单控件、hover、focus、expanded 和 disabled 状态。
- 在真实数据和真实宽度下观察整体色块关系；局部组件符合规范不代表整页协调。
- 每次只解决已经确认的问题，不用新的设计主张替代用户已经表达的偏好。

### 1.2 奥卡姆剃刀的含义

简化的目标是用最少的视觉和文字信号完整表达结构，而不是一味删除边框或压缩空间。

- 每一层只保留一个必要的分组信号。
- 不同时叠加背景色、外框、阴影和内部卡片。
- 删除不会影响用户判断或操作的副标题、技术字段、重复标签和装饰性状态。
- 重要状态、风险和操作结果必须保留，不能为了简洁而降低可理解性。

## 2. 视觉语言

### 2.1 颜色与 Surface

- 使用 `web/src/styles.css` 中的语义变量，不在功能组件中创造相近但不一致的灰色或白色。
- `--paper` 用于页面背景或导航层，`--paper-accent` 用于主要内容 Surface 和表单控件。
- Settings 右侧内容、展开内容和输入控件使用统一的 `--paper-accent`；左侧导航可使用 `--paper` 建立区域区分。
- 避免把白色卡片放在仅有轻微色差的灰色内容底上，形成“补丁”效果。
- 状态色只用于状态本身：success、warning、danger、info 不应成为大面积装饰背景。
- 暗色模式必须使用对应语义变量，不能写死只适用于亮色模式的白色或灰色。

### 2.2 边框、圆角与阴影

- 默认使用 `--line` 的一层弱边框表达容器边界。
- 控件与设置容器采用 `--control-radius`，当前为 8px，对应常用的 `rounded-md`。
- 同一页面不要混用多套显著不同的圆角尺度。
- 设置页保持低层级、低装饰；默认不使用阴影，抽屉本身等需要表达浮层关系的场景除外。
- 分隔线应服务于字段或章节区分；能用间距表达时，不额外增加分隔线。

### 2.3 密度与间距

- 目标是平衡可读密度，不追求极端紧凑或展示型大留白。
- 同级设置项使用统一的标题高度、左右内边距、圆角和垂直间距。
- 紧凑列表只保留识别和操作所需的信息；例如定向同步列表默认显示期刊名，不重复展示 RSS URL。
- 页面不得产生页面级横向溢出；局部宽表可使用明确的内部横向滚动。

## 3. HeroUI 使用规范

HeroUI 负责可访问性、键盘行为、焦点管理、ARIA 语义和基础交互。项目自己的语义变量、圆角和密度负责最终视觉。

- 优先使用 HeroUI 已有组件，不重复实现 Button、Chip、Disclosure、Accordion、Checkbox、Select 等基础交互。
- 使用组件前检查项目当前 HeroUI 版本的官方文档和 API。
- 不直接照搬官方展示页的渐变、大圆角、阴影或 Surface 色阶。
- 显式检查组件默认、hover、focus-visible、expanded、loading、disabled 和 error 状态；默认 variant 也可能与项目视觉冲突。
- 状态使用 `Chip`，操作使用 `Button`，危险操作使用 danger 样式，不用普通文字模拟组件状态。

### 3.1 Disclosure 与 Accordion

- 单个可折叠设置统一使用共享的 `AdminDisclosure`。
- 同级 Disclosure 必须具有相同的边框、8px 圆角、标题高度、箭头和内容间距。
- 标题背景在收起、展开和 hover 时保持透明；展开状态主要由箭头和内容出现表达。
- 默认保持收起，除非既有产品行为或用户明确要求展开。配置缺失、错误或状态变化不能自动成为展开理由。
- 内容必须与标题属于同一个容器，避免标题和内容形成两个嵌套卡片。
- 只有确实需要组级状态管理或单项互斥时才使用 Accordion；不能仅因为页面上有多个折叠项就把它们合成一个 Accordion。
- App 中的 Zotero、Scheduled sync、Local app 是三个独立 Disclosure，与其他 Settings 页面使用相同视觉规格。

## 4. 信息架构与文案

- 使用稳定的页面导航和单列主内容；常用设置直接呈现，技术设置渐进披露。
- 避免卡片套卡片、表单套卡片和重复的大标题层级。
- 同一个概念只命名一次。例如 `Latest activity` 下不再重复 `Latest job`。
- 副标题必须解释用户当前需要作出的决定；纯描述性或从控件本身即可推断的文字应删除。
- 用户在当前迭代中明确删除的帮助文字、徽章或装饰标签，不得自行重新加入。
- 技术诊断信息集中放置，不应阻断高频任务。

### 4.1 渐进披露

- 折叠低频、技术性或危险范围较大的设置，不折叠当前任务所需的关键信息与主要动作。
- 展开后仍只显示有决策价值的信息。例如 Scheduled sync 只需显示启用状态、时间和上次运行时间，不展示任务名、命令等内部字段。
- 错误详情位于摘要之后；成功或空状态不应被大块技术信息占据。

## 5. 操作与产品行为

- 不因视觉重构擅自改变默认展开、跳转、聚焦、保存或请求条件。
- 独立表单只采用一种明确保存方式，避免自动保存和显式保存混用。
- Remove、Delete、Disable、Stop 等破坏性或中断性动作使用 danger 样式。
- 下载按钮只在确有可下载更新时出现，不能以看似禁用的状态长期占位。
- `Generate profile proposal` 只在生成任务运行中禁用；开放反馈数为 0 时仍允许运行，并明确显示 `0 feedback`。
- 长时间 LLM 操作保持为后台任务，并在 UI 中显示进度、等待人工验证、停止和最终结果。
- 环境变量控制的字段应统一禁用并说明来源，不能让用户误以为界面保存会覆盖环境配置。

## 6. 页面职责与当前布局基线

### 6.1 阅读工作区

- 主界面采用三栏布局：左侧筛选、中央论文列表、右侧详情。
- 中央列表默认使用 `Unread + Last 30 days`，采用虚拟列表；论文卡只显示摘要，不放置行内动作。
- `DOI link`、`Mark as read`、`Save to Zotero`、`Mark wrong` 由右侧详情面板负责。
- 如果已有 Profile，三栏工作区应立即渲染，论文列表不得等待非关键 Admin 数据。
- 如果没有 Profile，先显示 onboarding；如果没有 RSS feed，应等待 feed 加载结束后再进入 feed 初始化空状态。

### 6.2 Settings

- Settings 保持右侧抽屉和 `Dashboard`、`Feeds`、`Profile`、`Model`、`App` 五个稳定顶层页面。
- 桌面使用左侧导航，窄屏退化为横向标签；标题、导航和关闭按钮固定，仅右侧内容滚动。
- Admin 负责 feed 编辑、手动任务、反馈、Profile proposal 和应用配置。
- Dashboard 优先展示运行中任务、验证状态和主要 Sync；定向 Sync、Reclassify、用量等低频项渐进披露。
- Feeds 使用独立本地草稿；取消必须恢复已保存值，未保存修改不能污染阅读状态。
- Profile 使用一个主要审阅文档；反馈队列位于下方作为次级区域。
- Model 常显连接与默认模型，低频调优和价格进入 Advanced，并使用一个统一保存动作。
- App 顶部常显 About、更新和运行信息；Zotero、Scheduled sync、Local app 使用相同的独立 Disclosure。
- Zotero 使用 Web API 和应用内 collection picker，不依赖浏览器 connector。

### 6.3 Onboarding 与 Profile

- Profile proposal 优先保证可审阅性，不以原始 JSON 作为主要呈现。
- 当前 Profile 或 pending proposal 只使用一个主要文档容器。
- 避免 onboarding、Profile、proposal review 中的 card-inside-card 或 box-inside-box。
- 通过轻量章节组织规则，压缩说明性 chrome，尽可能缩短页面。

## 7. 性能与代码边界

- `/api/report/latest` 是首屏关键路径；保持批量读取，不得重新引入逐论文查询或请求级 SQLite 反复打开关闭。
- app update、scheduler、settings、proposal 和 feedback 属于非关键后台加载，不能阻塞论文列表。
- 在 `web/src/app/App.tsx` 和 `web/src/main.tsx` 中，顶层 helper 与组件保留简短中文注释说明职责。
- UI 行为变化应同步更新 `ARCHITECTURE.md`；用户可感知的改进应记录在 `CHANGELOG.md` 当前未发布版本。

## 8. 视觉验证

视觉比较必须使用等价数据状态，不能用空状态与 populated 状态比较密度。

每次较大的 UI 改动至少检查：

- 1440、1024、768px 下的布局与滚动行为。
- 默认、hover、focus-visible、展开、收起、disabled、loading、error、empty 状态。
- 标题、正文、输入框和 Surface 是否出现不协调的色块或圆角。
- Tab 顺序、Esc 关闭、焦点归还以及 Disclosure/Accordion 的键盘操作。
- 长标题、长 URL、较多 feed、较多反馈和错误详情。
- 页面级 `scrollWidth`，确认没有横向溢出。

前端行为发生变化时，按风险运行：

```powershell
corepack pnpm --dir web test
corepack pnpm --dir web build
git diff --check
```

构建产生的用户级 pnpm `EPERM` 配置读取警告不等于失败；应以命令退出状态和实际构建结果为准。

## 9. 实施前检查清单

- 是否先确认了真正的问题层级，而不是从某个视觉属性开始试错？
- 是否复用了现有 HeroUI 组件和项目语义变量？
- 是否引入了未经要求的默认行为或自动展开？
- 是否保留了完成任务所需的信息，同时删除了重复信息？
- 是否统一检查了整页，而不是只调整单个组件？
- 是否使用相同数据状态和目标宽度完成视觉比较？
- 是否验证了交互状态、可访问性和横向溢出？
